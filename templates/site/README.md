# templates/site: stage 0 of the website / Stufe 0 der Website

**DE.** Vorlage und Anleitung fuer freesynergy.net, helfa.org, freeplanetearth.org (DNS bei Hetzner, Auslieferung per Zentinel `static-files`). Es gibt **keine Platzhalter- oder "Im Umbau"-Seiten** im Repo: Die Eingabe von `site-bauen` ist ein Ordnerstand, den ein Mensch freigegeben hat. Die Hostnamen stehen **nur** in `site.toml` im Wurzelordner jedes Pakets (Schema unten); Vorlage, Skripte und Tests nennen keinen Host. **TODO (Mensch, vor dem Live-Gang):** echte Inhalte, Impressum und Datenschutz (ob und was Pflicht ist, entscheidet der Mensch; nichts davon ist hier erfunden). Keine Geheimnisse in diesem Ordner.

### Weg einer Seite

1. `site-bauen` (CI-Job `build`, kein Schluessel): Ordner pruefen (Erlaubnisliste der Dateitypen, keine Punktdateien, im Modus `static` als **Erlaubnisliste**: nur die Tags, Attribute und URL-Formen, die der Exporter fs-text-html schreibt; kein svg/math/style/script/noscript/template, kein Kommentar, jede Adresse relativ ohne Backslash, CSS ohne `url()`, `@import`, Escapes; und jede Seite traegt ihre **eigene** `<meta>`-CSP als erstes Element nach `<meta charset>`. Zentinel 26.11_2 sendet auf statischen Routen keine CSP, diese Pruefung ist die einzige Wand), Tarball bauen (sortiert, Eigentuemer 0, mtime = Release-Zeit `SITE_MTIME` = Commit-Zeit des freigegebenen Standes, Rechte 0644/0755; die Release-Zeit steht im Manifest, damit sich der ETag des Servers (Groesse + mtime) mit jedem Release aendert), zweimal bauen und byteweise vergleichen. Modus `--passthrough` nur ausdruecklich fuer eigenes HTML mit JavaScript: gleiche Dateitypen-Liste plus `js`/`mjs`, jede Datei wird mit Hash im Protokoll genannt, die CSP ist dann die zweite Wand (siehe unten).
2. Der Mensch schreibt die Freigabe (`gate`, `name`, `version`, `mode`, `tree-sha256`, `tar-sha256`, `run-id`, `expires`) und signiert sie getrennt (`gpg --armor --detach-sign`) mit dem Freigabe-**Unterschluessel**. `tar-sha256` ist der Hash der Tarball-Datei selbst (die Bytes); `run-id` ist die Kennung `<GITHUB_RUN_ID>-<GITHUB_RUN_ATTEMPT>` des Bau-Laufs, sie kommt aus der CI, nie von einem Agenten. Gueltig hoechstens 72 Stunden **ab Signaturzeit**.
3. `site-signieren` (CI-Job `sign`, Umgebung `site-signing` mit Pflicht-Freigabe): `scripts/site-freigabe-pruefen.sh` (ohne Schluessel in der Umgebung), dann Neubau aus dem freigegebenen Git-Stand mit Byte-Vergleich (alles als eigener Schritt `--check-only`, ohne Schluessel auf dem Runner), danach legt ein Schritt (nur er hat die Secrets in der Umgebung, nur Shell-Builtins) den Schluessel als 0600-Datei ab und der Signier-Schritt bekommt nur den Dateipfad: kein Prozess haelt den Schluessel in `/proc/<pid>/environ`. Der Job gibt ausserdem `kdl-sha256` (staging, production, http-only) der Zentinel-Konfiguration aus, gerendert aus der `site.toml` des geprueften Tarballs (Repository-Variable `SITE_ACME_EMAIL`). dist enthaelt genau vier Dateien (Tarball, Manifest, SPDX, SHA256SUMS.txt); der Tarball darf nur normale Dateien und Ordner enthalten (keine Links, Geraete, Sonderrechte, 0777-Ordner, absolute oder `..`-Pfade), geprueft **vor** dem Entpacken.
4. Der Mensch liefert aus (kein Agent, kein SSH durch eine KI): `scripts/site-signaturen-pruefen.sh`, `sha256sum --check SHA256SUMS.txt`, dann
   `mkdir /srv/www/<domain>/releases/<version>` (ohne `-p`: der Ordner muss **neu und leer** sein, sonst legt tar den neuen Stand ueber den alten; ist er da, abbrechen), dann `tar -xzf <name>-<version>-site.tar.gz --no-same-owner --no-same-permissions -C /srv/www/<domain>/releases/<version>` und atomar tauschen: `ln -sfn releases/<version> /srv/www/<domain>/current.new && mv -T /srv/www/<domain>/current.new /srv/www/<domain>/current` (Weg zurueck: der alte Link), **danach immer `zentinel reload`** (SIGHUP): ohne Reload liefert Zentinel nach dem Tausch den alten Inhalt aus dem Cache (gemessen mit 26.11_2; eine gleich grosse Datei behaelt ETag und Last-Modified). `test-podman.sh` zeigt es. Seiten behalten `cache-control: max-age=300`; langlebige Dateien gehoeren unter eine inhaltsadressierte URL (`/_fs/<hash>/...`), nie unter einen festen Namen. `If-None-Match`, `If-Modified-Since` und Range ergeben in 26.11_2 nie 304. Die Zentinel-Wurzel jeder Domain ist `/srv/www/<domain>/current`.
5. Zentinel-Konfiguration (Port 80 = echter 301, Zertifikate, CSP) liegt **nicht** im signierten Tarball (sie enthaelt Serverwerte und aendert sich selten). Sie wird aus dem gepinnten main (`git verify-commit`) mit `render.sh` und der `site.toml` aus dem signierten Tarball erzeugt, vom Menschen gelesen; ihr Hash (`<datei>.sha256`) muss dem `kdl-sha256` aus der Zusammenfassung des Sign-Jobs entsprechen (zwei Seiten), wird im Protokoll festgehalten und auf dem Server verglichen. `render.sh` kopiert keine Seiten und erzeugt Routen, Zertifikate und Kopfzeilen aus den `site.toml`-Dateien (`render.sh [--staging|--production|--http-only] --site <site.toml> ... <ausgabe.kdl>`; die fruehere Option `--install-pages` gibt es nicht mehr: kein ungeprueftes Kopieren aus Git am Signaturweg vorbei).

### Woher kommen Liste, Schluesselbund, Skript, Lauf-Kennung

- Skripte, `configs/site/allowed-signing-keys.txt` (Fingerprints des Freigabe-**Unterschluessels**, `gpg --list-keys --with-subkey-fingerprints`; ein Software-Unterschluessel unter demselben Hauptschluessel zaehlt nicht, wenn er nicht gelistet ist) und `configs/site/approvers.pgp` (binaerer, nur lesbarer Schluesselbund, `gpg --export`) kommen aus dem gepinnten `main`; die CI laeuft nur auf `main`. **Das `if: main` der Jobs schuetzt nicht** (wer einen Branch pushen kann, startet die `site.yml` dieses Branches ohne das `if`); die Wand ist die Deployment-Branch-Regel der Umgebung `site-signing` (nur `main`, Pflicht-Pruefer, Selbstpruefung aus, Secrets nur dort) plus geschuetztes `main`. Eine Aenderung der Liste ist ein Commit, den der Mensch signiert. Die Dateien fehlen noch (TODO Mensch); solange ist der Lauf rot.
- Vor dem ersten echten Lauf schriftlich belegen: der Freigabe-Unterschluessel liegt auf einem Token mit Beruehrungspflicht oder einem anderen Geraet und ist unter der UID der Agenten nicht nutzbar (auch nicht ueber einen gpg-agent mit gemerkter Passphrase). Nichts im Skript kann das pruefen.
- Die Lauf-Kennung ist eine Eingabe des Starters (workflow_dispatch), nicht aus der CI abgeleitet; das Pruefskript erzwingt nur das Format `<id>-<versuch>` und dass es nicht der Signier-Lauf selbst ist. Der Schutz sind die Bytes (`tar-sha256`) plus die 72 Stunden; ein Wiedereinspielen derselben Freigabe innerhalb von 72 Stunden signiert dieselben Bytes noch einmal.
- Eingabe `folder` des Workflows: der Standard `.` ist immer rot (die Pruefung lehnt `.git` ab); immer einen ausdruecklichen Unterordner angeben, z. B. `folder: site-out`.

### Zentinel auf dem Server (Mensch, Reihenfolge)

Nur das signierte Mirror-Release (fs-zentinel v26.11_2, .deb + .asc, mit `verify-mirror.sh` pruefen). Die Hinweise folgen fs-zentinel `examples/README.md`.

1. **Erster Start ohne ACME.** Mit ACME in der Konfiguration bricht Zentinel ab, wenn die erste Ausstellung scheitert (fs-zentinel `examples/README.md:16`). Zuerst `render.sh --http-only /etc/zentinel/zentinel.kdl`, `zentinel test -c`, Start; die Seite muss ueber die Server-IP mit `Host:`-Kopf kommen. Port 80 muss erreichbar sein.
2. **DNS vorher setzen** (Hetzner DNS, durch den Menschen): A-Eintraege der drei Domains auf den Server, warten bis sichtbar (`dig +short <domain> @1.1.1.1`).
3. **AAAA klaeren.** Die Vorlage lauscht nur auf IPv4 (`0.0.0.0`). Let's Encrypt bevorzugt IPv6, wenn ein AAAA-Eintrag existiert: bestehende AAAA-Eintraege (z. B. vom alten Server) entfernen, oder die Listener auch auf IPv6 binden und beides pruefen.
4. **Rechte.** Zentinel laeuft als Nutzer `zentinel` (Ports 80/443 ueber `CAP_NET_BIND_SERVICE` der systemd-Einheit, laut fs-zentinel). `/var/lib/zentinel/acme` ist der `StateDirectory` der Einheit (Besitzer `zentinel`, Modus 0700; alle drei ACME-Bloecke teilen sich diesen Ordner). Vor dem Start pruefen: `systemctl cat zentinel`, `ls -ld /var/lib/zentinel/acme /srv/www/<domain>`. Die Wurzel muss fuer `zentinel` lesbar sein (der Tarball erzwingt 0644/0755), und `zentinel` darf dort nicht schreiben.
5. **Staging zuerst.** `render.sh --staging` (Standard), `zentinel test -c`, Neustart, `journalctl -u zentinel`; Staging-Zertifikate pruefen (`openssl s_client -connect <domain>:443 -servername <domain>`, Aussteller "(STAGING)"). Erst dann Produktion: Dienst stoppen, `rm -rf /var/lib/zentinel/acme/*` (Konto und Zertifikate des Staging), `render.sh --production`, `zentinel test -c`, Start. Nicht wiederholen ohne Not (Rate-Limits).
6. **Port 80** ist ein Namespace-Listener mit Redirect-Filter: echter 301 auf `https://<host>/<pfad>`; der Query-String geht verloren. Gemessen mit 26.11_2 (`test-podman.sh`, `messung-zentinel-stufe1.md`): GET, HEAD, POST, PUT geben 301 (kein 307/308), IPv6 `[::1]` ebenso, auch unbekannte Hosts bekommen 301; ACME-HTTP-01 auf diesem Listener wird **vor** dem 301 beantwortet (Pebble, 3 von 3; unbekanntes Token gibt 301); im Log steht dabei harmlos `ERROR ACME challenge served, status: 500` neben der Antwort 200. Gegen das echte Let's Encrypt **nicht belegt**, bis der Staging-Lauf es zeigt. Schlaegt die Erneuerung fehl, zurueck zu `--http-only` und Ursache klaeren.

### Content-Security-Policy (Einstellung)

`render.sh` setzt pro Seite eine CSP als Antwortkopf der Route, gesteuert durch `site.toml` `[csp] mode` (`static`, Standard, streng: keine Skripte, nichts von aussen, kein Rahmen; oder `passthrough`: eigene Skripte der Seite, `script-src 'self'`, `connect-src 'self'`) und `[csp] policy` (eigene vollstaendige Policy, Zeichen streng geprueft). **`passthrough` lehnt `render.sh` ab**, solange nicht ausdruecklich `--allow-passthrough` steht (mit Warnung). **Wirkt in 26.11_2 nicht:** Zentinel sendet die Header-Regeln (CSP, nosniff, Referrer-Policy) auf statischen Routen nicht (vier Varianten gemessen: Route-policies, Filter response/both, Namespace-Filter; nur Upstream-Routen setzen sie; `test-podman.sh` meldet es als NOTE). Die Einstellung steht trotzdem in der Konfiguration und besteht `zentinel test -c`; sie greift, sobald Upstream es behebt. Notnagel und Pflicht im Modus `static`: jede Seite traegt eine eigene `<meta http-equiv="Content-Security-Policy">` (strikt: `default-src` nur `'self'`/`'none'`, kein Inline-Skript; die Ordnerpruefung verlangt sie als erstes Element nach `<meta charset>`; `frame-ancestors` geht per Meta nicht). Bis dahin kein `passthrough` live schalten. Upstream-Anfrage (Workflow `upstream-anfrage`) mit dieser Beobachtung steht aus. Fuer `static` traegt die Ordnerpruefung (Erlaubnisliste plus Pflicht-Meta-CSP).

### site.toml: der einzige Ort der Hostnamen (die Naht fuer spaeteres automatisches DNS)

Jedes Paket hat `site.toml` im Wurzelordner (Teil des signierten Tarballs; die Ordnerpruefung verlangt es und prueft es mit `scripts/site_manifest.py`). Schema, Beispiel und Regeln: `site-toml-schema.md` im selben Ordner. Kurz: `schema = 1`, `purpose = "website"`, `[names] primary, aliases`, `[dns] records` (gewuenschte Typen A/AAAA/CAA), `[acme] method = "http-01"` (`dns-01` ist reserviert und wird abgelehnt), `[csp] mode, policy`. `render.py` erzeugt daraus Zertifikatsbloecke (Haupt- plus Aliasnamen), eine Route je Name und die Kopfzeilen. **Spaeter:** ein `DnsProvider`-Adapter (fs-server, ADR 0088; Hetzner Cloud API zuerst) liest dieselben `site.toml`-Dateien aus den ausgelieferten Paketen (`/srv/www/<primary>/current/site.toml`, oder aus dem Artefakt) und legt die Eintraege nach `names` und `dns.records` an; `acme.method = dns-01` kommt dann als zweiter Wert dazu. In diesem Auftrag gibt es keinen DNS-Code, keinen Hetzner-Zugriff und kein Token.

**EN.** Template and guide for the three domains (DNS at Hetzner, delivery by Zentinel `static-files`). **No placeholder pages are kept in the repo**: the input of `site-bauen` is a folder state a person approved. **TODO (person, before going live):** real contents, imprint and privacy text (what is required is the person's decision; nothing is invented here). No secrets in this folder.

Path of a page: (1) `site-bauen`, CI job `build`, no key: allowlist of file types, no dot files, static mode an ALLOWLIST of tags, attributes, URL forms and CSS (what the exporter writes) plus a mandatory page-own `<meta>` CSP (Zentinel 26.11_2 sends no CSP on static routes, so this is the only wall), deterministic tarball built twice and compared; `--passthrough` only explicitly for the person's own HTML with JavaScript, every file logged with its hash. (2) The person signs the approval (detached) with the approval **subkey**; it names the bytes of the tarball (`tar-sha256`), the content hash, name, version, mode and the build run id from the CI; valid 72 hours from the **signature time**. (3) `site-signieren`, CI job `sign`, protected environment `site-signing`: approval check without the key in the environment, rebuild from the approved git state with a byte comparison, only then the key; dist holds exactly four files; the tarball allowlist (plain files and folders only) runs before unpacking. (4) The person delivers by hand into `/srv/www/<domain>/releases/<version>` and swaps `current` atomically; Zentinel roots are `/srv/www/<domain>/current`. (5) The Zentinel configuration is not in the tarball: rendered by `render.sh` from the pinned main, read by the person, its `.sha256` recorded and compared on the server.

Provenance: scripts, `configs/site/allowed-signing-keys.txt` (fingerprints of the approval subkey) and `configs/site/approvers.pgp` come from the pinned main (CI runs on main only; a change of the list is a commit the person signs; the files do not exist yet: TODO person, the run is red until then). The person documents before the first real run that the approval subkey is not usable under the agents' UID. The run id is enforced by the check script in CI.

Server order: first start with `--http-only` (ACME would stop the start when the first certificate fails), DNS (A records) before staging, clarify AAAA (IPv4-only listeners: remove AAAA or bind IPv6), check owner and mode of `/var/lib/zentinel/acme` (service user `zentinel`, StateDirectory 0700) and of the webroot, staging first, then production after emptying the ACME state. Port 80 is a real 301 (query string lost; measured with 26.11_2 on a high port for GET, HEAD, POST); ACME HTTP-01 on that listener and IPv6 are **not proven** until the staging run. The CSP is a setting per site (`csp.mode` / `csp.policy` in `site.toml`; `passthrough` is refused by `render.sh` without `--allow-passthrough`); measured: 26.11_2 does not send route response headers for `static-files`, so the setting only takes effect with a version that does (upstream request pending); do not put passthrough pages live before. Tests: `scripts/test-site.sh`, `test-podman.sh`.

Host names live **only** in `site.toml` at the root of each package (part of the signed tarball; schema in `site-toml-schema.md`); templates, scripts and tests name no host. `render.sh [--staging|--production|--http-only] --site <site.toml> ... <out.kdl>` generates certificates (primary plus aliases), one route per name and the headers from them. A later DnsProvider adapter (fs-server, ADR 0088) reads the same files (names, wanted record types A/AAAA/CAA) and manages the records; `acme.method = dns-01` is reserved. Delivery: after EVERY swap of `current` run `zentinel reload` (SIGHUP), otherwise Zentinel serves the old content from its cache (measured with 26.11_2; same-size files keep ETag and Last-Modified; shown by `test-podman.sh`); the tarball carries the release time (commit time) as mtime so the ETag changes per release; pages keep `cache-control: max-age=300`; 304 never happens in 26.11_2. CSP/nosniff/referrer headers do **not** work on static routes in 26.11_2 (four variants measured); the setting stays, takes effect with an upstream fix; generated pages should carry a meta CSP as a stopgap. Port 80: 301 for GET/HEAD/POST/PUT, IPv6 and unknown hosts alike; ACME HTTP-01 is answered before the 301 (Pebble, 3 of 3); not yet proven against the real Let's Encrypt.
