# Crate index: the registry `freesynergy` (repo `FreeSynergy-Net/fs-crates`)

Why: cargo knows version ranges only through a registry. With a registry, a new type in `fs-types` no longer forces ~25 repos to re-tag (decision ENTSCHEID-kaskade B2, 23 Nov. 2026). Consumers write `fs-types = { version = "~0.0.N", registry = "freesynergy" }`.

## What is in the repo `fs-crates`

- `config.json` (once, by the owner of the repo): `{ "dl": "https://raw.githubusercontent.com/FreeSynergy-Net/fs-crates/main/crates/{crate}/{crate}-{version}.crate" }` (no `api`: nobody runs `cargo publish` against it).
- the index: one file per crate in the layout of the cargo registry index (`fs/-t/fs-types`, one JSON line per version: name, vers, deps, features, `cksum` = SHA-256 of the `.crate`, yanked).
- `crates/<crate>/<crate>-<version>.crate`: the packaged crates.
- `allowed-sources.txt`: the allow list `owner/repo <first version> <package>...` (packages in dependency order). It is part of the trust set (see below).
- `.github/workflows/index.yml`: the workflow that fills the registry (template: `templates/fs-crates/` in fs-release, with README on how it gets there).

## How a crate gets in: PULL, not push (decision of the strategy, review K-2/K-3)

No secret (`FS_CRATES_TOKEN` does not exist) and no write right across repos. The workflow runs IN `fs-crates` every 15 minutes (`schedule`) and by `Run workflow` (`workflow_dispatch`, one click for the user). Nobody dispatches it from outside. The project bot `LordKalEl-Bot` keeps write right on `fs-crates` (maintain, given per repo; ADR 0093 addendum 2026-11-23 (3)). The workflow is the usual writer, but the bot is not prevented from writing directly.

- Job `tool` (`contents: read`, r3): builds `fs-crate-index` from the pinned fs-release WITHOUT a checkout of fs-crates or of a source repo and WITHOUT a cache, uploads it as its own artifact and gives its `sha256` as the job output (and the toolchain name).
- Job `package` (`contents: read`, `needs: tool`): takes the tool from `tool` (sha256 checked), `fs-crate-index scan`: `git ls-remote --tags` of the repos on the allow list; for every new tag `vX.Y.Z` (not older than the first version of the allow list) it checks: the tag is annotated, the tag commit is on `main` of the source repo, the tag equals the version of every listed package, the version is not in the index yet, and the tag was not moved after an earlier entry (the tag commit is in the commit message of the entry: `source: owner/repo vX.Y.Z commit <sha> tag-object <sha>`; a different commit now is red and nothing is entered again). Then `cargo package --locked` for all listed packages in ONE call (interdependent packages verify against each other, before any of them is in the index), then the semver gate (below); red = no entry. Output: `plan.txt` and the `.crate` files as an artifact, WITHOUT the tool (`setup-rust` runs with `cache: "false"`: foreign build code runs here and its state is never saved for a later run).
- Job `enter` (`contents: write`, `needs: [tool, package]`): the toolchain is fixed first (`setup-rust`, `cache: "false"`, and `RUSTUP_TOOLCHAIN` in the step `enter`), then the tool from job `tool` is checked with `sha256sum -c` against `needs.tool.outputs.sha256` (RED if it differs; actionlint cannot check this, only the chain of digests is evidence). `fs-crate-index apply` builds nothing; the only cargo call is `cargo metadata --no-deps` of `reg-index` inside the unpacked `.crate`, with the fixed toolchain (a `rust-toolchain.toml` in the `.crate` cannot choose the compiler). It re-checks every plan line against the allow list and the tag (a tag that moved between the jobs is red), enters the crates one after the other in the order of the allow list (S6: a later package needs the earlier one already in the index, else "dependency not found in index"), one commit each, then ONE push, never forced. The token lives only in the push step and in no other job. This is a job split, not a sandbox: on a GitHub-hosted runner any process of the same job could read the token from the runner. That is why job `enter` runs only the checked tool and no source build code.
- HONEST limit (r3, review M1): the CONTENT of the `.crate` files of a run is decided by the code that runs in job `package`: `cargo package` and cargo-semver-checks compile the source crates, so their `build.rs` and proc-macros and those of their crates.io dependencies run there, as the same user in the same `$RUNNER_TEMP` (where the checked tool lies). Whoever controls a source repo on the allow list (`main` + annotated tag) or such a dependency decides the `.crate` files of that run; with several source repos in one run also those of the OTHER repos (an own job per source repo would be the remedy; it is not built). `apply` cannot check the content of a `.crate`. What the job split does guarantee (table "Identity of an entry" below, each value with test and mutant): the tool that enters them is not theirs, and name, version, source repo and tag commit of an entry are checked against the plan and the allow list, not believed from the `.crate`.
- A red tag blocks all later tags (S3): `scan` stops at the first bad tag of the whole run (`break`), so one lightweight tag, a tag off `main`, a semver-red tag or a moved tag makes the run red every 15 minutes and later tags of ALL source repos are not entered, not even `v0.0.(n+1)`. Way out: delete the bad tag in the source repo, or raise the first version of that line in `allowed-sources.txt` above the bad tag by a reviewed pull request.
- By rule nothing is written by hand (the project bot has write right, so this is a rule, not a lock; see Threat model). A version already in the index is never replaced. A rerun does nothing new (idempotent).
- The format work is done by the library `reg-index` 0.6.0 (the library of `cargo-index`, MIT OR Apache-2.0, pinned `=0.6.0`); our tool is the adapter with the checks above. Index format: `reg-index` writes v1 lines; the adapter moves every feature whose values use `dep:` or `?/` into `features2` and sets `v: 2` (registry-index standard). A crate with an optional dependency (like `fs-records`) is therefore fine. Test: three crates that mirror fs-types, fs-conformance, fs-records, resolved by a fresh consumer with the feature switched on.
- The workflow cannot be called today: the old `uses:` pin `78992eea` does not know `crates/fs-crate-index`. The template carries the placeholder `FS_RELEASE_PIN`, which is set BY HAND (40 hex) after the merge: `pin-refs.sh` refuses an unknown pin since main 28b665fe (rc 3), so it does not replace the placeholder (README of the template).

### The semver gate: ONE implementation (`actions/semver-baseline`, `fs-crate-index semver`)

The baseline is ALWAYS the newest (not yanked) version of the crate in the registry, unpacked from its `.crate` (`--baseline-root`), never a git tag. `cargo-semver-checks` v0.51.0 is installed in one place only (the action: pinned binary, sha256 checked) and runs with `--release-type minor`. Three cases, each tested (`crates/fs-crate-index/tests/semver.rs`):
1. registry reachable, crate has NO version: green, the log says `no baseline: first registry version`;
2. registry reachable, version present: compared with it (`--release-type minor`); red = no entry;
3. registry not reachable (clone fails, no `config.json`): RED with its own text (`REGISTRY NOT REACHABLE` / `NOT READABLE`), never confused with case 1.
A baseline without a `cargo-semver-checks` binary is `NOT RUN`, never green: the subcommand `semver` is red, and `scan` has `--semver-checks` as a REQUIRED argument (r3, M2: the tool does not even start without it) and is red with nothing planned if the outcome is `NOT RUN` (test `scan_without_the_semver_binary_is_red_when_a_baseline_exists_and_plans_nothing`, mutants "NOT RUN allowed" and "flag optional" are red). Self test: a red stand-in and the mutants "unreachable counts as no baseline" and "comparison skipped" turn tests red (evidence in the report). The checked branch must not release itself: the lint level of cargo-semver-checks stands in the `Cargo.toml` of the checked package (`metadata.cargo-semver-checks.lints`), so the gate reads EVERY manifest of the source first and is RED if ANY `cargo-semver-checks` table is there (`check_manifest_lints`; r3, M3: not even `enum_variant_added = "warn"`, because with `warn` the tool reports the hit but does not fail, and the filter by type is not built, so a new variant of any exhaustive enum such as `ZoneKind` would be green; mutant test: `warn`, `allow`, another lint, a table form, `[lints.cargo-semver-checks]` and a workspace table are all red and cargo-semver-checks is not called). Consequence, honest: a new variant in `BasicType` or `CommandKind` (capnpc-generated, ADR 0093) is a deliberate, visible break (a version step) until the filter by type (allow list of exactly these two types, applied to the output of the tool) is built; it belongs HERE in fs-release, not in the checked repo. No allow file for the gate exists: a red gate is fixed in the code or by a version step, not by an exception.
The pull job in `fs-crates` uses the action (without `package`: install and build) and the tool's `scan`, which calls the same function. The early signal in the publisher repo (`fs-types`, `semver.yml`) calls the action with `package`, `registry` and `source-dir`; that connection is built in the fs-types repo by another order (nothing is copied: replace its own `--baseline-rev` call by the action).

### What the release flow waits for

`ff-und-tag` / `release-beobachten` waits for the index line (a read, no right needed): `fs-crate-index wait --registry-url <fs-crates> --package fs-types --version <v> --minutes 20`. After the time it prints the blocker: "BLOCKED: ... The index workflow in fs-crates is switched off or late (GitHub switches scheduled workflows off after 60 days without activity in the repo; cron can be late). One click: open <workflow page>, press `Enable workflow` if it is off, then `Run workflow`." The tool exists and is tested. NOT YET DONE: the call in `workflows/ff-und-tag.yaml` step `release-beobachten` (summary line 223 ff.) and its Rust helper `release-watch`; that is a separate order (workflow-pflege) because it changes a workflow other flows depend on.

## Consumer

`.cargo/config.toml` of the repo (and of every generated program):

```toml
[registries.freesynergy]
index = "https://github.com/FreeSynergy-Net/fs-crates"
```

This string must be the same everywhere (it is also the `index-url` the tool writes into the entries: a dependency of a registry crate on the same registry is stored as "same registry" only if the URLs are equal) and it is the value of `[only_from] fs-types` in `scripts/lock-sources.toml`; the lock shows it as `registry+https://github.com/FreeSynergy-Net/fs-crates`.

IMPORTANT for the publishing repo (K-4): the path dependencies between the published crates need `registry = "freesynergy"` next to `version` (`fs-types = { path = "../fs-types", version = "0.0.7", registry = "freesynergy" }`) and `.cargo/config.toml` with the registry. Without `registry`, cargo treats the dependency as one from crates.io and the index line points there. The test in `crates/fs-crate-index/tests` uses exactly this form. fs-types `unreviewed/k4-version-gate-r1` (1dc9b435) has `path` and `version` only: to be fixed there.

## Threat model (honest)

The registry protects against MISTAKES (a wrong tag, a replayed or moved tag, a tag not on main, a `.crate` that was changed afterwards by accident: cargo refuses it because the checksum of the index does not match). It does NOT protect against someone who can change the workflow, the toolchain or the scripts, and not against someone who can write to `fs-crates`: the checksum lies in the same repo as the `.crate`, so whoever can push there can swap a crate and its checksum together. Therefore the trust set is: the people and accounts who can write to `fs-crates` (this includes the project bot `LordKalEl-Bot`, maintain right, ADR 0093 addendum 2026-11-23 (3)) or change its workflow or `allowed-sources.txt`. The registry protects against mistakes, not against them. Cargo checks the checksum against the index, not against a signature. The pull path makes the set smaller than the push path: no secret in the publisher repos, no right across repos, and the tool that enters the crates is built apart from any source code and checked by its sha256. It does NOT make a wrong publisher repo harmless: the source crates are compiled in job `package`, so the repos on the allow list and the crates.io dependencies with build code of the listed crates are part of the trust set too, for the content of the `.crate` files of the run (not for the allow list or `allowed-sources.txt`, which by rule only a reviewed change of `fs-crates` writes (no lock: whoever can write to `fs-crates`, the bot included, can change it), and not for entries already in the index: a version in the index is never replaced, test `a_version_already_in_the_index_is_never_replaced`). A lock protects only a consumer that already has it (case 2 is red); a FRESH consumer without a lock accepts a swapped version (case 3, test `case_2_index_and_crate_swapped_together_with_an_old_lock_is_red_and_case_3_fresh_consumer_accepts_it`).

### Identity of an entry: where each value comes from, and against what it is compared

Class of defect (review r3, M1): an identity is believed from the content of an untrusted artifact (a `.crate` or `plan.txt` from job `package`) instead of from the plan of the tag and the allow list. Every value that goes into an entry is compared in `apply` (job `enter`) BEFORE the entry is written. A mutant means: the comparison is replaced by `true`, the named test turns red (run at r4, local).

| Value | Comes from | Compared before the entry against | Where | Test | Mutant |
|---|---|---|---|---|---|
| Name | inner `Cargo.toml` of the `.crate` (artifact content, untrusted) | package of the plan line, which must be on the allow list for that repo | `apply.rs:49-52` (plan line vs allow list), `apply.rs:66-72` (name in the `.crate` == package) | `identity.rs:42` (`a_crate_whose_inner_name_differs_from_the_plan_line_...`: name `not-on-any-list` and the name of another allowed package) | name check `true`: red (NEW in r4) |
| Name (file) | file name in `plan.txt` | `{package}-{version}.crate`, so no other path | `apply.rs:61-64` | `identity.rs:96` | file-name check `true`: red (NEW in r4) |
| Version | tag of the plan line, inner `Cargo.toml` of the `.crate` | version of the tag (plan), inner version == tag version, tag not older than the first version of the allow list | `apply.rs:53-60` (plan vs tag), `publish.rs:114` (inner version vs tag) | `identity.rs:63` (plan), `guards.rs:88` (inner: tag v0.0.9 with a 0.0.7 `.crate`) | plan check `true`: red (NEW test); inner check `true`: `guards.rs:88` red |
| Source repo | `plan.txt` (untrusted) | allow list of `fs-crates` (file of the checkout, not of the artifact), and `ls-remote` of exactly that repo | `apply.rs:49-52`, `apply.rs:73-76` | `guards.rs:138` | `s.repo == repo` replaced by `true`: red |
| Tag SHA (tag object and commit) | `plan.txt` (untrusted) | `ls-remote` of the source repo at the time of `apply`: tag object AND commit | `apply.rs:77-80` | `pull.rs:72` (tag moved between the jobs) | whole comparison `true`: red |

Not covered, honest: the CONTENT of the `.crate` (source code) is decided by job `package` (see above); the allow list check does not make it harmless. The name test also covers the swap between two allowed packages (content of `demo-lib` under the file name of `demo-base`).

## raw.githubusercontent.com as the download place [U: not measured]

Only `dl` points there; the index itself is fetched by cargo as a git repo from `github.com`. [U] means untested: a live download, the content type, a Windows runner and a proxy were never measured; this is assumed from reading, not from a run. Dependencies and limits: (1) every build of every consumer downloads each `.crate` once per cargo home (cargo caches), so a CI without cache downloads per run; raw.githubusercontent.com has no published contract for this use, its rate limits are not guaranteed and a block shows as a failed download; (2) it follows the default branch name `main`: a rename breaks every old lock-free build (a lock stores the checksum, not the URL, so existing locks keep working after the URL is fixed); (3) behind a proxy or on a Windows runner the host must be allowed; (4) for a PUBLIC repo it needs no token. Fallbacks, each a change of `config.json` only: release assets of `fs-crates` (cargo follows redirects; `dl` then needs a FIXED release tag as the collecting place, and GitHub limits the number of assets per release), or a static host in front of Zentinel. Cargo's git index fetch from github.com uses a fast path through `api.github.com` (60 requests per hour without a token per IP) and falls back to a full git fetch if that is limited: slower, not red.
